# NerdHealth

Evidence search for training and nutrition, for curious people: find a study, ask a
question, look up a food, sketch an illustrative plan. It shows what the research says. It
is not a coach and not a dietitian.

**The spec is `docs/PLAN.md`. Read it, and `docs/PROGRESS.md`, before any work.**

---

## How work happens

The project is built in **stages** (`docs/PLAN.md` §7), one at a time, in order. Run a stage
with `/stage N`; the skill holds the full cycle. The short version:

1. One branch per stage: `stage/N-short-name`.
2. Plan first, approved by Nicolas, before any code.
3. **Tests first**, tagged with the requirements they verify, and seen to fail.
4. Implement until `make check` is green.
5. The `stage-reviewer` agent reviews the stage with a clean context. Its findings are fixed,
   not argued with, unless they are wrong, in which case say why in `PROGRESS.md`.
6. Close the stage in `requirements.yaml`, update `docs/PROGRESS.md`, open the PR.
7. **Stop.** Never start the next stage without being asked.

A stage is done when `make check` passes with the stage marked `done`. Not when the code
looks finished.

## Where things are

| File | What it is | Who writes it |
|---|---|---|
| `docs/PLAN.md` | the spec: requirements, stages, tests, CI/CD | frozen; changed only by a PR that says why |
| `requirements.yaml` | every requirement, its stage, how it is verified; stage status | the stage that delivers it |
| `docs/TRACEABILITY.md` | requirement → tests → status | **generated by `make check`. Never edit it.** |
| `docs/PROGRESS.md` | current stage, what is left, decisions and why | updated at the end of every session |

Tag every test that verifies a requirement:

```python
@pytest.mark.req("F5", "F16")
def test_empty_retrieval_abstains() -> None: ...
```

An unknown ID fails collection. Skipped and xfail tests never count as verification.

## Non-negotiables

These override making the build green.

- **"I don't know" is a correct answer.** Never make a test pass by weakening abstention,
  loosening the grounding check, or letting a model answer from memory.
- **No number reaches an answer unless a tool produced it.** Missing values are reported
  as missing, never as 0.
- **Never lower a threshold in `evals/thresholds.yaml` to make CI pass.** A shortfall is
  written into `docs/results.md` with its reason.
- **Never skip, xfail or delete a failing test to get green.** Fix the code, or stop and say
  the test is wrong.
- **If the spec is wrong, stop and propose a change to `docs/PLAN.md`.** Never deviate from
  it silently.
- **No secrets in the repository**, not even in tests or fixtures.

## Conventions

- **English everywhere**: code, comments, docs, commits, branch names.
- **Conventional Commits**: `feat:`, `fix:`, `test:`, `docs:`, `chore:`, `ci:`, with the
  stage as scope: `test(stage-3): known-item recall on the mini-corpus`.
- Small commits. Tests in the same PR as the code they verify.
- `main` is always green. Never commit to it directly.
- Python 3.12, `uv`, Ruff, mypy strict. Type every function.

## Commands

```bash
uv sync                 # install
make check              # the gate: starts services, lint, types, tests, secret scan, traceability
make check-fast         # lint, types, unit tests only; not the gate
make up / make down     # Qdrant (6343) and Postgres (5442) via docker compose
make test               # pytest only (integration tests fail if services are down)
uv run pytest -m req    # only requirement tests
uv run python -m evals.run --mode <search|ask|food|oob|router> [--target module:callable]
                        # golden set -> reports/eval/<mode>.{json,md}; exit 1 below threshold
```

More commands arrive with each stage (`docker compose up` in Stage 0, `make eval` in
Stage 1). Add them here in the stage that creates them.
